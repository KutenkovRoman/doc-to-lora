### 1. idefics2.py

Все изменения находятся в классе `Idefics2Perceiver`
В `__init__` захардкодил параметры для сэмплирования случайных матриц, их смысл:
- `n_reprs` — сколько матриц (представлений) использовать для каждого чанка контекста (в моей терминологии контексты бьются на чанки, чанки не на что не бьются)
- `n_layers`, `in_features`, `out_features` — количество слоев и размеры матрицы весов для модулей, которые модифицируем
- `r` — ранг для малоранговых представлений (других пока нет)

То есть для каждого контекста сэмплируется `n_chunks * n_reprs` пар матриц `A` и `B` с размерами `(r, out_features)` и `(in_features, r)` соответственно. Затем прогоняем `A` через `modality_projection` и перемножаем их, чтобы прогнать через `encoder`. Это решение очень сомнительное, ведь умножение этих матриц как будто противоречит идее с малоранговым разложением (чтобы не материлизовывать полную матрицу), но пока не понятно, как можно было бы по-другому, ведь мы хотим, чтобы `queries` в `encoder`-е имели возможность смотреть на полученные представления. Еще момент что тут везде используется sequence packing, то есть нужно вот эти спроецированные матрицы конкатенировать вдоль столбцов (это делается с помощью `view`) и задать для них `position_ids`, сейчас я их задаю так, что для каждого чанка его `n_reprs` матриц лежат в одной последовательности (то есть между ними как-то считаются attention-ы), и у меня получается `n_chunks` последовательностей (не знаю, как это нормально объяснить, надеюсь, что с пониманием sequence packing-а хоть что-то понятно). После прохождения через `encoder` мы прибавляем полученные латенты к латентам контекстов (можно было бы конкатенировать).

В `forward` добавил несколько параметров, необходимых для сэмплирования:
- `n_ctx_chunks` — тензор размера `(n_ctx,)` (количество контекстов до дробления на чанки), в нем хранится число чанков, на которое был разбит каждый контекст в данном батче
- `repr_seeds` — тензор размера `(n_ctx,)`, в нем хранится `seed` для каждого контекста (без учета чанков, на которые он разбит), этот `seed` используется для сэмплирования для данного контекста
- `generator` — объект генератора, он общий для всех, у него используется метод `manual_seed` для воспроизводимости (сейчас матрицы не сохраняются при сэмплировании и повторно сэмплируются в форвард пассе модели)

Основная проблема в том, что прохождение через `encoder` происходит с `torch.no_grad()`, ведь иначе промежуточные активации заполняют память и все падает с OOM для 80GB. Еще это все в сетапе иголки, где используется `ctx_encoder_type=early_exit`, то есть мы берем активации базовой модели только с одного слоя (6-ого для геммы), если брать активации со всех слоев, то расходуется намного больше памяти (еще даже до сэмплирования матриц, у меня получалось 63/80GB, тогда как для текущего где-то 9/80GB) и ничего не помещается. Мне кажется, что идея с тем, чтобы `queries` `encoder`-а смотрели на сэмплированные матрицы имеет смысл, но текущая имплементация не справляется, нужно как-то ее менять.

### 2. aggregator.py

Тут по сути добавил параметры в `forward`, которые просто передаются `forward`-у персивера

Из особенностей то, что в режиме `ctx_encoder_type=per_layer_activation` тензор `features` имеет размерность `n_layers` (с каждого слоя приходят свои `features`), однако перед тем, как передать их в `forward` персивера, делается `rearrange` и размерности `n_layers` и `seq_len` сливаются. По сути это означает, что у нас число чанков как бы умножается на `n_layers`, ведь для каждого слоя как бы используются свои чанки (поэтому в `__init__` в этом режиме `n_output_queries = num_modules * self.r` без умножения на `num_layers`). Для нашей архитектуры это означает, что в режиме `ctx_encoder_type=early_exit` все `n_reprs` представлений общие для всех слоев. В режиме `ctx_encoder_type=per_layer_activation` можно в `forward` персивера добавить цикл по `n_layers` и сэмплировать для каждого слоя свои матрицы, но в этом режиме проблемы с памятью. Почему нельзя (точнее проблематично) делать так же в режиме `early_exit`: после прохождения через `encoder` получается "слишком много" латентов и суммирование ломается, ведь мы получим в `n_layers` раз больше латентов, чем ожидается. Можно было бы как-то использовать не сумму, а конкатенацию, но с учетом всех проблем выше не факт, что это хоть как-то поможет

### 3. hypernet.py

Тут изменения в двух классах: `HyperLoRA` и `ModulatedPretrainedModel`. В основном это прокидывание параметров `n_ctx_chunks`, `repr_seeds` и `generator` из одного `forward`-а в другой. В методе `ModulatedPretrainedModel.generate_weights` добавлен подсчет сидов по токенизированным контекстам, по сути мы просто складываем все токены, котоые относятся к одному контексту и используем результат в качестве `seed`-а (даже в задаче с иголкой, где в качестве наполнителя используется одна и та же фраза, вроде бы получаются разные сиды, скорее всего это связано с чанкином и упаковкой).

Еще из архитектурных изменений я использовал `per_rank_gen=False`, она используется для генерации одноранговых лор и убирает фиктивную размерность ранга. Также я поменял голову, теперь она предсказывает для каждого слоя и каждого контекста коэффициенты, с которыми мы суммируем случайные малоранговые добавки к весам. То есть у нас для каждого контекста есть `n_chunks * n_reprs` представлений, которые общие для всех слоев, но у каждого слоя свои предсказанные коэффициенты (на каждый чанк сэмплируются свои `n_repr` представлений и для них предсказываются веса, но по итогу мы их все складываем в одну кучу, тут идея в том, что они почему-то не должны интерферировать друг с другом)

### 4. lora_layer.py

Добавил две функции: `apply_random_repr` и `random_repr_forward`, первая нужна сугубо для настройки второй. Во второй просто заново сэмплируем те же самые матрицы и уже по нормальному используем их малоранговое представление. Кажется, при таком подходе можно обойтись без отдельного шага с комбинированием коэффициентов.

За включение/отключение этого кода отвечает флаг `USE_RANDOM_REPR`, который лежит в `hypernet.py`. Если пытаться это запускать, то для экспа с иголкой нужно генерировать датасет, я пользовался уже сгенерированным, который лежал в соседней репозитории, поэтому я изменил пути по умолчанию в `data/definitions.py`
